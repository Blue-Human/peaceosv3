# PeaceOS Verify Desktop

A Tauri shell around [`@peaceos/web`](../web) for Windows, macOS and Linux.
This package contains **zero verification logic**: it opens a native window
that shows `web/dist` exactly as built for the browser portal (embedded
transparency registry included), and evidence verification runs entirely
inside the webview, in the same TypeScript `core`/`web` code the browser
portal uses.

The only thing this package adds on top of the browser portal is **one
Rust-side command**, `update_organizations_registry` — see below.

## Prerequisites (not needed just to read/edit this package)

Building or running the desktop shell requires the Rust toolchain and a
platform C toolchain, on top of the Node/pnpm setup the rest of the repo
uses:

- [Rust](https://www.rust-lang.org/tools/install) (stable) + Cargo.
- **Windows:** the "Desktop development with C++" workload from the Visual
  Studio Build Tools, and the [WebView2](https://developer.microsoft.com/microsoft-edge/webview2/)
  runtime (preinstalled on most current Windows systems).
- **macOS:** Xcode Command Line Tools (`xcode-select --install`).
- **Linux:** the packages Tauri's own
  [prerequisites guide](https://v2.tauri.app/start/prerequisites/) lists for
  your distro (WebKitGTK, etc.).

None of this is required to work on `web/` or `core/` — only to build the
desktop shell itself. The `web-build` CI job in this repo does **not**
exercise this package; see `.github/workflows/desktop-build.yml` for the one
that does, running on `windows-latest` / `macos-latest` / `ubuntu-latest`
where the toolchains above are already present.

## Commands

```bash
git submodule update --init transparency/registry   # first time only
pnpm install
pnpm --filter @peaceos/desktop run dev     # opens a dev window against the Vite dev server
pnpm --filter @peaceos/desktop run build   # produces installers under desktop/src-tauri/target/release/bundle
```

`tauri dev`/`tauri build` run `web`'s own `dev`/`build` scripts first
(`build.beforeDevCommand` / `build.beforeBuildCommand` in
[`src-tauri/tauri.conf.json`](./src-tauri/tauri.conf.json)), which is what
regenerates and embeds the transparency registry snapshot — exactly as the
browser portal does. There is no separate copy of the frontend here.

## No network, enforced twice

The browser portal never calls `fetch`/`XHR` during verification (see
`web/src/networkGuard.ts` and its tests). The desktop shell additionally sets
`connect-src 'none'` in the window's Content-Security-Policy
(`app.security.csp` in `tauri.conf.json`), so the webview is structurally
unable to make any network connection at all, from any code path — not just
during verification. This is stronger than the browser case, where a user
could in principle load a different page; here there's nowhere else to
navigate to.

One consequence during development: Vite's hot-reload websocket is also
network traffic, so it's blocked by this CSP under `tauri dev`. Reload the
window manually to see changes; this is a deliberate trade-off, not a bug.

The one explicit, user-triggered exception is the "Update organizations"
button, described next — implemented as a Rust-side Tauri command (the only
place in this app allowed to make an HTTPS request), never as a relaxation
of the webview's own CSP. The webview reaches it only through the two
narrow, typed commands below — it has no general `fetch`/`http` capability.

## Capabilities

[`src-tauri/capabilities/default.json`](./src-tauri/capabilities/default.json)
grants `core:default` (basic window functionality) plus exactly two
app-defined command permissions — `allow-update-organizations-registry` and
`allow-load-local-registry-state`, autogenerated by `build.rs` (via
`tauri_build::AppManifest::commands(...)`) for the two commands in
`registry_update.rs`. Every command in Tauri v2 — plugin-provided or not —
is denied by default unless a capability names it explicitly, so this is the
whole allowlist: no `fs`, `http`, or `shell` plugin is registered at all,
meaning there is no IPC surface that could reach the filesystem or the
network beyond exactly these two narrow, hard-coded commands, even if the
CSP were misconfigured.

## Updating the organizations registry

The "Update organizations" button in the transparency section (desktop only
— the browser portal has no backend to do this from) is the **only** action
in this whole app that touches the network, and only runs when the user
clicks it. `desktop/src-tauri/src/registry_update.rs` implements the whole
pipeline:

1. **Fetch** — resolves the latest commit of the fixed canonical source
   (`Blue-Human/peaceos_organizations`, hard-coded — never a URL supplied by
   the frontend), lists its tree in one GitHub API call, and downloads only
   `keys/<org_id>/<key_id>.pub` and `registry.manifest` from
   `raw.githubusercontent.com`. Nothing else in that repository (docs,
   scripts, revocation records, org metadata) is ever fetched.
2. **Validate, fail closed** — before anything is written: every key path
   matches `keys/<org_id>/<key_id>.pub` with a restrictive slug alphabet (no
   traversal possible), every key is exactly 32 non-zero bytes, nothing
   downloaded matches known private-key/secret-material shapes (PEM banners,
   a 64-byte opaque secret-key size, BIP39-looking mnemonic lines — mirroring
   `transparency/registry/scripts/lib.mjs`'s own `scanForSecrets`), and every
   key's SHA-256 matches its entry in `registry.manifest` with no entries on
   either side left unaccounted for. **Any** failure aborts before touching
   disk — the previously-stored local copy, if any, is left exactly as it
   was.
3. **Persist** — writes to a staging directory under the app's data
   directory, then swaps it into place (restoring the previous copy if the
   swap itself fails), so the active registry is never left missing or
   half-written.

None of this re-implements or touches `core`'s verification logic — it only
prepares a local transparency snapshot for the same `resolveTransparencyTree`
resolution the browser portal already uses.

**Priority order** the app resolves transparency data in, on every
verification (`web/src/embeddedTransparency.ts`):

1. A copy the user loads manually (the "advanced option," same as the
   browser portal) — always wins.
2. The locally-updated copy from the last successful "Update organizations"
   run, if any (loaded from disk at startup via `load_local_registry_state`).
3. The registry embedded in the app at build time (the factory default).

The UI always shows which of these is active and its date/commit, and warns
(via `web/src/desktopRegistry.ts`'s `isRegistryStale`, default threshold 28
days) when the active registry is old — independent of the source, and shown
in the browser portal too.

### Dependencies this adds

Beyond what Tauri itself needs: `ureq` (HTTPS client; default features give
pure-Rust TLS via `rustls`, no system OpenSSL dependency), `sha2` (SHA-256,
RustCrypto), `serde`/`serde_json` (IPC serialization and parsing GitHub's API
responses). Base64-encoding key bytes for the IPC payload to the frontend is
hand-rolled (`base64_encode` in `registry_update.rs`, with RFC 4648 test
vectors) rather than adding a fifth crate for it — it's an encoding of bytes
we already produced, not a cryptographic primitive.

### Testing this

```bash
cd desktop/src-tauri
cargo test
```

Runs entirely against the pure Rust logic (no Tauri app context needed —
`persist_snapshot`/`read_local_snapshot` take a plain `Path`), including:
unit tests that feed `validate_snapshot` deliberately tampered snapshots
(wrong key size, all-zero key, manifest hash mismatch, a key missing from
the manifest or vice versa, a PEM private-key banner smuggled into a `.pub`
file) and assert rejection; a persistence round-trip proving a failed update
never touches a previously-good local copy; and one test that calls
`download_registry_snapshot()` for real against
`Blue-Human/peaceos_organizations` over HTTPS (this one needs network
access — it's what CI's `desktop-build.yml` exercises on all three OSes).

`cargo test` doesn't exercise Tauri's IPC/capability layer itself (there's
no trivial way to construct a real `AppHandle` in a unit test). CI closes
that gap with a Windows-only step
(`desktop/ci/verify-update.mjs`) that launches the actual compiled `.exe`
with WebView2 remote debugging enabled, drives it over CDP with
Playwright, clicks the real "Update organizations" button, and confirms the
registry actually updates and still verifies evidence afterwards.
`desktop/ci/` is deliberately outside the pnpm workspace (not listed in
`pnpm-workspace.yaml`) and its own tiny `package.json` installs
`playwright-core` fresh in CI — it's automation tooling for this repo's CI,
not a dependency of the shipped app.
